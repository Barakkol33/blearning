Chapter 1 · Hi-tech vocabulary

Where software lives

Frontend

The part you see and click: screens, buttons, the app on your phone.

Backend

The part you don't see: logic and data, running on servers.

API

The agreed "menu" one program uses to ask another for something.

Database

Organised storage for all the data: users, orders, messages.

Cloud

Renting computers over the internet instead of buying your own.

SaaS

Software you subscribe to and use online — nothing to install.

The idea

Almost every app is split in two. The part on your phone or in your browser is the client, built by frontend developers. It is mostly a window: when you tap "my orders", it sends a request over the internet to a server.

The server runs the backend — the real logic. It checks who you are, fetches your orders from the database, and sends the answer back.

API

The request and the answer follow agreed rules called an API. Think of a restaurant menu: you can only order what is on it, in the way it is written, and the kitchen knows exactly what to bring.

Cloud and SaaS

Companies rarely own these servers any more. They rent them from Amazon (AWS), Microsoft (Azure) or Google — that is "the cloud". Software delivered this way, by subscription, is called SaaS (Software as a Service). The opposite is software installed on the customer's own servers, called "self-hosted" or "on-prem".

Chapter 1 · Hi-tech vocabulary

How a tech team works

R&D

Research & Development: the engineering organisation that builds the product.

Product Manager

Decides what to build and why. The voice of the customer.

Agile

Working in small steps and adjusting often, not one big plan.

Sprint

A short, fixed work cycle (often two weeks) with a clear goal.

Backlog

The prioritised list of everything waiting to be built.

Stand-up (daily)

A 15-minute sync: what I did, what's next, what's blocking me.

QA

Quality Assurance: testing before customers see it.

Roadmap

The high-level plan for the coming quarters.

The idea

Software teams don't plan a year ahead in detail. They work Agile: build a little, show it, learn, adjust.

The work waits in a prioritised list called the backlog. Every couple of weeks the team pulls the top items into a sprint and commits to finishing them. Each morning there is a short stand-up meeting to stay in sync. At the end, something working is released.

Who is involved

  • R&D — the engineers who build the product.
  • Product Manager (PM) — decides what should be built and in what order.
  • QA — tests that it really works.
  • Team Lead / Engineering Manager — manages the engineers.

Why it matters to you

When a manager says "we can't interview this week, it's the end of the sprint", this is what they mean. It also explains why teams want hires to start at the beginning of a cycle.

Chapter 1 · Hi-tech vocabulary

Programming words you'll hear daily

Programming language

How developers write instructions: Java, Python, JavaScript, Go, C++.

Library / framework

Ready-made code that developers build on instead of starting from zero.

Bug

A mistake in the code that makes software misbehave. Fixing it is "debugging".

Feature

One capability of the product: "export to PDF", "dark mode".

Deploy

Putting a new version onto servers so it can actually be used.

Full-stack

A developer who works on both the frontend and the backend.

Environments

The same software exists in several copies. Developers work in dev, where breaking things is fine. Staging is a realistic rehearsal. Production ("prod") is the real thing customers use — when someone says "production is down", it is an emergency. Moving a version from one to the next is called deploying.

Versions

Every release gets a number such as 2.4.1. The first number changes for big changes, the middle one for new features, the last for small fixes.

Languages

A programming language is simply the language code is written in. Different jobs favour different ones: JavaScript for web screens, Java and Go for backends, Python for data and AI. In a CV, languages and frameworks (ready-made foundations such as React or Spring) are the main "skills" keywords.

Bug or feature?

A feature is something the product is meant to do. A bug is when it does something it shouldn't.

The idea

There are many programming languages for the same reason there are many tools in a toolbox: each is good at something. The drawing groups the common names by where they are used; the cards say what each one is mainly for.

The languages

  • Python — reads almost like English. The default for data analysis, AI and small automation scripts.
  • JavaScript — the only language browsers run, so every website uses it. TypeScript is JavaScript with extra safety checks.
  • Node.js — not a language: it lets JavaScript run on a server, so one team can write both frontend and backend in the same language.
  • Java — the workhorse of banks, insurers and large enterprises. Systems written in it live for decades.
  • Go — created at Google for cloud software. Docker and Kubernetes are written in it, so DevOps people love it.
  • C and C++ — old, fast and close to the machine. Used where speed or hardware matter: operating systems, cars, chips, game engines.

Not languages: the tools around them

Every language has a package manager that downloads the outside code a project needs, and often a build tool. Maven does both for Java (Gradle is its rival). npm is the one for JavaScript, pip for Python. These names come back in the chapter on packages.

Reading a CV

  • A language is not a seniority level; "5 years of Java" says more than "Java".
  • A good developer learns a new language in weeks. Learning its whole world — frameworks, tools, habits — takes longer, which is why teams ask for specific experience.
  • Group what you see by the columns in the drawing: it tells you what kind of developer this is.
Chapter 1 · Hi-tech vocabulary

The business side of hi-tech

Startup

A young company searching for a product that can grow fast.

Funding round

Investors (VCs) put in money in return for shares: Seed, A, B, C…

Unicorn

A private startup valued at more than one billion dollars.

IPO / Exit

Going public on the stock market, or being bought by another company.

B2B / B2C

Selling to businesses, or selling directly to consumers.

ARR

Annual Recurring Revenue: yearly subscription income.

Equity / options

A share in the company given to employees, earned ("vested") over time.

Headcount

The number of approved positions a team is allowed to fill.

The idea

A startup is not just a small company — it is a company built to grow quickly, usually on investors' money rather than profits.

The drawing shows the usual path. Each step up is a funding round: venture capital funds (VCs) invest, and in return get a share of the company. The rounds have names — Seed, A, B, C — and each one is larger. The path ends in an IPO (shares sold on the stock market) or an exit by acquisition.

How the company earns

B2B companies sell to other businesses; B2C sell to the public. Most B2B software is sold by subscription, so the number everyone watches is ARR — the subscription income for a year. Churn is the share of customers who leave.

Why it matters to you

Compensation in hi-tech usually includes equity: options or shares (RSUs) that vest over about four years. Hiring follows the funding cycle — a new round usually opens new headcount; a tight market freezes it.

Think of a restaurant. Someone designs the menu, cooks prepare the dish, it gets tasted, a waiter brings it to the table, and the manager watches whether guests are happy. Software works the same way — thousands of times a day.

The idea

Whatever the product — a banking app, a game, the software in a car — it travels the same six steps: someone plans it, developers code it, the code is built into something that can run, it is tested, released to users, and then run and watched.

Then the loop starts again, because users always want something new and something is always broken.

The restaurant

Menu design, cooking, tasting, serving, and watching the dining room. A good restaurant does this smoothly hundreds of times a night. A good software company does it thousands of times a day.

Why it matters

Everything else in this deck — DevOps, packages, containers — is about making this road faster and safer.

Chapter 2 · What is DevOps?

The old way: two teams and a wall

Dev · Developers

"Ship new features, fast."

Wrote the code, then handed it over and moved on to the next thing.

THE WALL
Ops · Operations

"Keep everything stable."

Ran the software for customers. Every change was a risk to avoid.

🐢 Slow

A new version once or twice a year.

💥 Risky

Huge releases — when they broke, they broke big.

👉 Blame

"It worked on my machine" vs. "your code broke production."

The idea

Until roughly 15 years ago, most companies had two separate groups with opposite goals.

Developers were rewarded for delivering new things. Operations were rewarded for keeping systems stable — and every new thing is a threat to stability. Developers finished their code and "threw it over the wall".

What went wrong

  • Releases were rare and huge, so each one was frightening.
  • When something failed, each side blamed the other.
  • Customers waited months for small improvements.

"It works on my machine" became the industry's running joke: the code ran on the developer's laptop but not in production.

Chapter 2 · What is DevOps?

Development + Operations, working as one

Not a tool and not really a job title — it's a way of working: one team owns the software from idea to customer, in a loop that never stops.

🤝 Culture

Shared responsibility: "you build it, you run it."

🤖 Automation

Machines do the repetitive building, testing and shipping.

⚡ Small & often

Many tiny updates a day instead of one giant yearly release.

The idea

DevOps removes the wall. One team is responsible for the software all the way from idea to customer — "you build it, you run it". The drawing is the famous infinity loop: the work never ends, it circles.

Three ingredients

  • Culture — shared goals and shared responsibility.
  • Automation — the boring, error-prone steps (building, testing, shipping) are done by machines, the same way every time.
  • Small and often — tiny changes many times a day. A small change is easy to check and easy to undo.

Common confusion

DevOps is a way of working, but you will also see "DevOps Engineer" as a job title. That person builds and maintains the automation the rest of the team relies on.

Chapter 2 · What is DevOps?

Keeping it running

Monitoring

Dashboards and logs that show how the system is behaving right now.

Alert

An automatic alarm when a number crosses a limit.

On-call

The engineer whose turn it is to respond — day or night.

Incident

Something is broken for customers. Top priority until it is fixed.

Rollback

Going back to the previous version that worked.

SLA / uptime

The promised availability, for example "99.9% of the time".

The idea

Shipping software is only half of DevOps. The "Ops" half is keeping it healthy while real customers use it, around the clock.

Reading the drawing

The green line is a measurement — here, the number of errors. Monitoring tools draw lines like this for thousands of measurements. When one crosses a threshold, an alert fires and the on-call engineer's phone rings.

That starts an incident. The team either fixes the problem or does a rollback to the last good version — which is quick, because releases are small. Afterwards they write a post-mortem: what happened and how to prevent it, without blaming a person.

Promises to customers

An SLA (Service Level Agreement) is the availability the company commits to. "Three nines" — 99.9% — allows less than nine hours of downtime in a whole year.

Why it matters to you

On-call duty affects people's lives: nights, weekends, sometimes extra pay. It is a normal topic in interviews and in compensation discussions for DevOps and SRE roles.

Chapter 3 · Code & packages

What is "code", really?

📝 Source code = a recipe

Text instructions written by developers in a programming language. People can read it; a computer can't run it as-is.

🕰️ Git = track changes for code

Every change is saved with who made it, when and why — so hundreds of people can edit together safely.

Word you'll hearWhat it means
Repository ("repo")The project's folder with its full history. Lives on sites like GitHub or GitLab.
CommitOne saved change — "fixed the login button".
Pull request (PR)"Please review my change before it joins the main version."

The idea

Source code is text. Developers type instructions in a programming language, and that text is the company's most valuable asset.

Git

Because many people edit the same text at once, they need a system that remembers every change. That system is Git. The project and its entire history live in a repository, usually hosted on GitHub, GitLab or Bitbucket.

Reading the drawing

The black line is "main" — the official version. Each dot is a commit, one saved change with a short message. To work safely, a developer creates a branch (the green line), a private copy. When ready, they open a pull request: colleagues review the change, and it is then merged back into main.

Good to know

"Code review" is this checking by colleagues. It is a normal, daily part of the job, not a sign that something is wrong.

Chapter 3 · Code & packages

Nobody writes everything from scratch

70–90%

of a typical app is commonly estimated to be code written by someone else.

📦 Package

A ready-made piece of code that solves one problem — sending email, drawing a chart, handling payments — wrapped up so others can reuse it.

🔗 Dependency

A package your software needs in order to work. Packages depend on other packages, which depend on others… easily hundreds deep.

🏪 Registry

The public "app store" developers download packages from.

npm · JavaScriptPyPI · PythonMaven · JavaDocker Hub · containers
The chef doesn't grow the wheat. A restaurant buys flour and spices from suppliers and focuses on its own dishes. Packages are the ingredients; package management is knowing what's in the pantry.

The idea

No team writes everything itself. For almost any common task there is already a package — a ready-made piece of code, usually open source, meaning it is published freely for anyone to use.

When your software uses a package, that package is a dependency. Packages have their own dependencies, as the tree shows, so one app can easily rest on hundreds or thousands of them.

Where they come from

Developers download packages from public registries. Each language has its own: npm for JavaScript, PyPI for Python, Maven Central for Java, Docker Hub for containers.

The restaurant

The chef buys flour instead of growing wheat. That is sensible — but it means the quality of the dish now depends on suppliers the chef has never met. Keep that thought; we come back to it at the end of this chapter.

Artifact (or "binary")

The output of a build: the actual file that gets installed and run. Artifacts are kept in an artifact repository.

CI/CD

Continuous Integration / Continuous Delivery: build, test and ship automatically, many times a day, with no manual copying of files.

The idea

Source code is a recipe; you cannot eat a recipe. The build combines the team's code with all its packages and produces the finished thing a computer can run. That output is called an artifact or binary.

Examples of artifacts: the app file you download to your phone, an installer, or a container image (a boxed-up program ready to run on a server — Docker is the best-known kind).

CI/CD

Nobody builds by hand. A CI/CD pipeline does it automatically whenever code changes: build, run tests, and if everything passes, deliver. Popular pipeline tools include Jenkins, GitHub Actions and GitLab CI.

Why it matters

Code lives in Git; the things built from code live in an artifact repository. Both have to be stored, versioned and protected.

Chapter 3 · Code & packages

Containers & Kubernetes

Container

A sealed box holding an app together with everything it needs to run.

Image

The stored, ready-to-run template of a container. It is an artifact.

Docker

The best-known tool for building and running containers.

Kubernetes (K8s)

A system that runs many containers and restarts them when they fail.

Microservices

One product built as many small programs, each in its own container.

Infrastructure as code

Servers and settings described in text files, kept in Git like code.

The idea

Remember "it works on my machine"? The cause is that the developer's laptop and the production server are set up differently. A container solves this by packing the app together with its packages and settings into one sealed box. The same box runs on a laptop, a test server and the cloud.

The name comes from shipping containers: the crane doesn't care what is inside, because every box has the same shape.

Image and Docker

The stored template of a container is an image — a kind of artifact. Docker is the tool that made containers popular, and "a Docker image" is how most people say it.

Kubernetes

A large product may run thousands of containers. Kubernetes (written K8s) is the system that manages them: you say "keep six copies running" and it does, starting a replacement when one dies. That is the right-hand drawing.

Related words

Microservices — splitting a product into many small services, each owned by a small team. Infrastructure as code — describing servers in text files, so environments can be rebuilt automatically. Common tool names you will see in CVs: Terraform, Helm, Ansible.

Chapter 3 · Code & packages

So many pieces. Who's keeping track?

A large company builds thousands of artifacts a day out of countless outside packages. That chain of ingredients is the software supply chain.

🗄️ Where is everything?

Which exact version did we ship to which customer? Can we rebuild it next year?

🕳️ Is it safe?

One flawed ingredient hits everyone who used it — like 2021's "Log4Shell" bug in a tiny, hugely popular Java package.

🎭 Is it genuine?

Attackers publish fake or poisoned packages, hoping developers download them by mistake.

The idea

Put the last slides together: thousands of builds a day, each made from hundreds of outside ingredients, written by strangers. This flow from the original authors to your customers is the software supply chain.

Three hard questions

  • Where is everything? If a customer reports a problem in a version from last year, can we find exactly that version and what went into it?
  • Is it safe? In December 2021 a flaw called Log4Shell was found in a small, free Java package used almost everywhere. Companies spent weeks just working out whether they were using it.
  • Is it genuine? Attackers upload packages with names that look like popular ones, hoping someone installs them by mistake.

The answer

A whole category of products exists to solve this: artifact repositories and supply-chain security tools that store, check and track every ingredient. The follow-up deck, JFrog 101, shows one company's answer.

The whole story in four lines

  • Software lives in two halves — frontend and backend — usually in the cloud, and is built by teams working in short sprints.
  • DevOps is the way of working that makes delivery fast and safe: shared ownership, automation, small frequent releases, and watching production.
  • Software is assembled from the team's own code plus many outside packages, built into artifacts, and often shipped in containers.
  • All those ingredients form a software supply chain that has to be tracked and protected.

A doorman for open-source. Blocks malicious or risky packages before a developer can download them.

While it's stored

JFrog Xray

An X-ray of every artifact: lists all the ingredients inside and flags known security holes and licence problems.

Deeper checks

JFrog Advanced Security

Finds leaked passwords, risky settings and flaws in the company's own code — and says which issues really matter.

Building security into the pipeline like this is often called DevSecOps.

The idea

If everything passes through one warehouse, that is the natural place to put the inspectors. Follow the drawing from left to right.

  • Curation stands at the door. When a developer asks for an outside package, it is checked against policy first. Malicious, too new, or badly maintained packages are turned away before they ever enter.
  • Xray examines what is already inside. It opens each artifact, lists every ingredient, and compares the list to databases of known security flaws (called CVEs) and to licence rules. When a new flaw is announced, it can say immediately which products contain it.
  • Advanced Security goes deeper: passwords accidentally left in code, risky configuration, weaknesses in the company's own code — and whether a flaw can actually be exploited, so teams fix what matters first.

The restaurant

The supplier check at the back door, the food-safety inspector in the pantry, and the allergen list on every dish.

A term to know

SBOM — Software Bill of Materials: the official ingredient list of a piece of software. Increasingly required by regulators and large customers.

The idea

Storing and checking is half the job; the software still has to reach where it runs.

  • Distribution packs a release into a sealed, signed bundle — nobody can change it on the way — and copies it efficiently to sites around the world, close to where it will be used.
  • Connect handles the "last mile" to physical devices: thousands of machines in the field that need updating remotely and reliably. This area is often called IoT (Internet of Things) or "edge".
  • JFrog ML brings AI into the same process. A machine-learning model is also a file that must be stored, versioned, secured and deployed. The practice is called MLOps.

The platform

Customers buy these together as the JFrog Platform, either as a cloud subscription or installed on their own servers.

The idea

These are the roles you will meet most often, both inside JFrog and at its customers.

Telling them apart

  • Developers create the product. Often split into frontend, backend and full-stack.
  • DevOps Engineers build the automated road the code travels on. Related titles: Platform Engineer, Build / Release Engineer.
  • SREs keep production healthy and are "on call" when it breaks.
  • Security people (AppSec, DevSecOps, researchers) find and prevent vulnerabilities.
  • Solutions Engineers and Developer Advocates are technical people who face customers and the community.
